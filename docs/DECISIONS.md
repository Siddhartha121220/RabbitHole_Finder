# Decision log

Newest last. Each entry: what we chose, what we rejected, why.

## Phase 0 — Scaffold
- **Chose** a single `backend/pyproject.toml` (uv, `uv_build` backend) with `Makefile` driving everything via `uv --directory backend`. **Rejected** a uv workspace at the repo root: only one Python package exists.
- **Chose** `pgvector/pgvector:pg17` and the official `ghcr.io/mlflow/mlflow` image with a SQLite backend in `./mlflow/` (gitignored). **Rejected** Postgres as MLflow backend: one less moving part locally.
- `make setup` skips `pnpm install` until `frontend/package.json` exists (Phase 8).

## Phase 1 — Ingestion & EDA
- **Feature month = the oldest of the 3 downloaded months (2026-07)**, not the latest. Graph, subset and stats come from it; 2026-08 and 2026-09 are reserved as LTR label months (§4.4). **Rejected** the spec's "most recent month" for the subset: it would leave no future months for leakage-free labels. Spec deviation, noted here.
- **Edge `p` is normalized over link clicks *within the subset*** (rows sum to 1, as the asset check requires). Raw `n` and per-article `onward_clicks` are kept, so Phase 4's absorbing chain can instead normalize by total onward clicks (which treats leaving the subset as leaving) if that proves more honest.
- **DEV subset BFS:** level by level, following each article's top-20 most-clicked links; the overflowing level is trimmed by summed click count. Deterministic and every article is reachable from a seed. **Rejected** global best-first search: it drifts into hubs.
- **Exclusions** (Main Page, disambiguation, lists, year/decade/date and "X in Y" year pages) are applied to BFS edges too, so they never enter the subset.
- **DEV text = lead section only** via `prop=extracts|info` (20 titles per call; `info` gives page byte length for `content_richness`). Chunks in DEV are therefore lead-only. **Rejected** full-page extracts in DEV: the API returns one full extract per request, i.e. ~5,000 requests.
- **Chunk size counted in words, not tokens** (~1.3 tokens/word). Avoids a tokenizer dependency; precise enough for retrieval.
- MediaWiki API: ≥1 s between requests, exponential backoff honouring `Retry-After` on 429/503/maxlag, every response cached to `data/raw/wiki_api/`. We were heavily 429'd with a placeholder contact in `WIKI_USER_AGENT`; it now points at the repo URL.
- FULL-mode HF streaming lives in `ingest/hf_text.py` with pyright in basic mode, because `datasets` lacks complete type hints. Implemented, not yet run.
- Added `marimo` (notebooks as plain `.py`, no stored outputs) and `matplotlib` (charts) as dev dependencies.

## Phase 2 — Graph & communities
- **Resolution chosen by modularity × coherence** among resolutions with median eligible size 20–200. **Rejected** max modularity alone: it always picked resolution 1, giving 23 communities in DEV (≈ one per seed topic, e.g. all of Rome and Byzantium together), which is too coarse for a rabbit hole. Coherence alone favours ever-smaller clusters. DEV result: resolution 4, 46 communities, 43 eligible, median size 68 (`reports/leiden_sweep.md`).
- **Coherence uses TF-IDF of lead texts for now**, not sentence embeddings (the spec's measure), because embeddings arrive in Phase 3. Re-run the sweep and notebook with embeddings then.
- **Central article = highest summed transition probability `p` from other members**, not raw weighted in-degree (spec deviation, spec updated). With raw counts, one huge edge crowned odd articles: "Hans Albert Einstein" for physics (via Albert Einstein's page), "Android 17" for software. With `p`, each member casts at most one vote: Albert Einstein, Linus Torvalds, The Beatles, Cricket, Charles Darwin.
- **c-TF-IDF has no `min_df`**: a word that appears in only one community is the best keyword, and `min_df=2` was silently removing exactly those (caught by a unit test).
- **Leiden vs HDBSCAN** (`notebooks/02_communities.py`): mostly the same topics (AMI ≈ 0.80). HDBSCAN on text wins raw stickiness (0.85 vs 0.71) but discards 43% of articles as noise (28% of views), mostly the bridging ones. On the same articles, Leiden has higher modularity (0.635 vs 0.602). Kept Leiden: it covers every article and rabbit holes are defined by reader movement. An honest "it's closer than expected" result.
- **Pruned serving graph:** top-10 outgoing edges per article by `p`; `cost = −log p + 0.1·log(1 + degree)` so hub pages cost more as stepping stones. Hub exclusion as bridge *endpoints* is left to Phase 5, where bridge paths are built.
- **Pyright:** switched to `typeCheckingMode = "strict"` with only the "unknown type from a library without stubs" rules off (igraph, scipy, scikit-learn and datasets have no complete hints). Everything else stays strict; the per-file `basic` override on `hf_text.py` is gone.

## Phase 3 — Embeddings, vector DB & map
- **CPU-only PyTorch** via a dedicated uv index (`pytorch-cpu`). **Rejected** the default Linux wheel: it bundles CUDA (~3 GB) for a GPU this project does not assume. GPU use goes through the export/import path instead (README).
- **Article embedding input = title + lead.** Chunks already start with their article title and section heading. Queries get bge's instruction prefix (configurable as `EMBEDDING_QUERY_PREFIX`); documents do not, as the model card recommends.
- **Shards are named by a content hash**, not a row offset. The offset version would have silently reused stale vectors when the DEV subset changed (it did, see below). Unchanged shards are never re-embedded, and nothing has to be deleted.
- **Vector width = `EMBEDDING_DIM` (default 384)**, used by the migration and checked against the model's output at embed time. **Rejected** loading the model inside the migration just to read its width: migrations should not need a 130 MB model.
- **Loader is idempotent:** upsert by id (only the columns provided, so Phase 4's `rh_score` survives a base-data reload), then prune rows that are no longer present. Articles whose id now maps to a different title are deleted first, because they would otherwise trip the unique-title constraint mid-upsert (covered by an integration test). `feedback` has no FK to `communities`, so user feedback outlives reloads. Every load writes a `pipeline_runs` row.
- **Map positions:** UMAP (cosine, 2D, fixed seed) on article embeddings; a community sits at the **mean of its members' positions**. **Rejected** a separate UMAP of centroids: centroids could land away from their own articles on the map.
- **Coherence now uses embeddings (spec), reported as lift over random pairs.** bge vectors are anisotropic: two random DEV articles have cosine ≈ 0.46, so raw coherence only moved 0.58 → 0.63 across the sweep and the modularity × coherence product collapsed to modularity alone, picking resolution 1 again. With lift (coherence − random-pair baseline) the score is nearly flat across resolutions 2–4 (0.096 / 0.092 / 0.094).
- **Resolution rule refined:** the finest resolution whose score is within 5% of the best (median size 20–200). When the metric cannot separate candidates, prefer smaller and more specific rabbit holes. It picks 4 on DEV, the partition reviewed in Phase 2. **Rejected** pinning 4 by hand in config: a rule carries over to FULL; a hand-pinned number would not.
- **Bug found by the acceptance probe:** the DEV seed `Mechanical_keyboard` is a redirect, so it never appears in clickstream and DEV had no keyboard articles ("mechanical keyboard" returned *Tonality* and *Electronic music*). Replaced with `Keyboard_technology`, the target page. Lesson for FULL: resolve redirects for any hand-written title.
- **Search tests run against a real Postgres** (a separate `rabbithole_test` database, created and dropped by the test). They skip, not fail, when no database is reachable.
- **Leiden vs HDBSCAN, re-run with embeddings** (HDBSCAN on a 10-d UMAP of bge vectors): AMI ≈ 0.69. HDBSCAN discards ~17% of articles as noise and wins raw stickiness (0.80 vs 0.71). On the shared articles, Leiden's modularity is clearly higher (0.68 vs 0.58). The Phase 2 conclusion holds, now with a wider margin.
- After the seed fix, DEV has 44 eligible communities (median 61 articles), including a new *Keyboard layout* rabbit hole (44 articles). The random sample in `reports/communities_sample.md` now shows different communities, because ids were renumbered and the fixed-seed sample picks by position.

## Phase 4 — Rabbit-holeness score
- **The Markov chain uses per-visit probabilities, `n(i→j) / views_in(i)`, not the edge table's `p`** (spec updated). `p` is normalized over link clicks inside the subset, so its rows sum to 1: nobody ever stops reading and expected depth is infinite or meaningless. Dividing by views keeps "stopped reading" and "clicked outside" as the absorbing mass, which is what "how deep do readers go" means. `max(views, onward_clicks) + 1` guards rows where onward clicks exceed views, so I − Q is always invertible.
- **Entry distribution π = each member's views minus visits from other members** (search, external, other-internal and links from outside the community).
- **Expected depth counts pages viewed inside, including the entry page.** DEV values are 1.0–1.45. They are low because clicks to the ~6M articles outside the 5k DEV subset count as leaving; FULL will raise them. Relative ordering is what the score uses (z-scores).
- **Discovery share = (other-internal + links from outside C) / (that + search)**: did readers wander in or search their way in?
- **Content richness uses the page's byte length** (`prop=info`, DEV). It inflates pages full of tables (World Cup results, rosters), which helps explain why *1998 FIFA World Cup* (10 articles) ranks #2. Kept for now; revisit with human labels. Readable prose length from FULL text would be fairer.
- **Correlations:** no score feature pair exceeds |r| = 0.85 (max: expected_depth vs stickiness, 0.79), so all six features stay. Popularity is excluded from the score as specified, and its correlation is shown only for reference.
- **Face validity (DEV):** the top 10 is the Beatles, 1998 World Cup, Minoan civilization, Epic Cycle, Heracles/Greek myth, Augustus/Rome, Byzantine Empire, UEFA Champions League, Zelda and the Trojan War. The bottom is look-up topics: Secret society, Keyboard layout, Nyotaimori, Costa Concordia disaster, Goalkeeper. Surprise: *Keyboard layout* scores low (onward ratio 0.17: people look up a layout and leave).
- **Labels:** blind CLI (`rabbithole label-communities`). It shows label, keywords and top articles but never the score, and is resumable (appends to `data/labels/rh_labels.csv`). **DEV has only 44 eligible communities**, so the 100-label study runs on FULL (Phase 9). Rating all 44 now is still useful for a first Spearman ρ.
- **Ridge-learned weights** (notebook 03) are only reported when ≥ 30 labels exist, cross-validated (5-fold), and adopted only if they clearly beat the hand-set weights.
- **Labelling scale changed from 1–5 to 1–7** (user request). Seven points give more spread for a rank correlation on a small sample. The tool also shows what each community is about (the opening sentence of its central article) and a one-line gist of every listed article, so unfamiliar topics can be rated fairly. The 13 ratings already given on 1–5 were moved to `data/labels/rh_labels_1to5.csv` (kept, not deleted) and are re-rated on 1–7, so no scales are mixed.

## Phase 5 — Recommender v1 + evaluation harness
- **In-memory catalog for ranking** (`recommend/catalog.py`, built from the pipeline's Parquet): article vectors, community centroids, rh_score, views and the pruned graph as a sparse matrix. Seeds from free text still go through pgvector (`recommend/seeds.py`). The same catalog will serve the API and the evaluation, so offline numbers measure the code users get.
- **Graph features from one multi-source Dijkstra** (scipy `csgraph`, `min_only=True`) per query, instead of a hop-limited custom search. The hop cap is applied afterwards by walking the predecessor tree. It is exact for the cheapest path. A path that is cheapest but longer than 6 hops counts as unreachable rather than falling back to a costlier short path; that is acceptable, since such bridges are not explainable anyway. Spec clarified: `graph_dist` is in hops (the cap was already in hops).
- **Hubs = articles linked from the most *different* communities** (top 0.5%), excluded as bridge endpoints. **Rejected** top in-degree: on DEV it flagged *Titanic*, *Chess* and *The Beatles*, the best entry points of their own rabbit holes. Distinct-community reach flags Europe, India, London, England, as intended.
- **Labels:** the label-month click graph is row-normalised over clicks inside the subset. The 3-step walk mass is summed over steps 2–3, with articles reached in step 1 zeroed (discovery, not visible links); grades are tertiles of positive mass per query. Label edges are their own pipeline asset (`label_edges`), built from months 2–3 on the feature month's ids. Nothing downstream of features reads it, so there is no leakage path.
- **"Relevant" = grade ≥ 2** for Recall, MRR and serendipity. **Rejected** grade ≥ 1: on DEV almost every reachable community gets some mass, which makes "relevant" meaningless.
- **Queries from a single community each** (spec said "same or neighbouring"). It is simpler and well-defined, with no neighbouring-community leakage across splits. Community split 60/20/20 with a fixed seed; eval uses test only, ready for LTR in Phase 9.
- **MLflow client = `mlflow-skinny`**, the tracking client without the server and UI (those run in Docker). One run per system in experiment `offline-eval`, with the report and chart as artifacts. If the server is down, logging is skipped with a warning; the Markdown report is the source of truth.
- **Second chart panel: accuracy vs serendipity.** Novelty (the spec's money chart) barely separates systems on DEV, so the trade-off the project is about shows up on serendipity instead.
- **Result:** v1 loses to nearest neighbour on accuracy, as expected given the proxy label, and beats random and popularity. Its serendipity is by far the highest. The Surprise slider moves accuracy monotonically (0.58 → 0.43 → 0.28). Bridge strength is the most useful feature. Bootstrap CIs are too narrow: 500 queries from 9 test communities are not independent. Full write-up in `docs/RESULTS.md`.
